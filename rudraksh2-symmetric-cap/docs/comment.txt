Subject: Re: Round1: Public Comment: Rudraksh2 - the 512 sets have only 256-bit symmetric strength, and the Cortex-M4 128/256 code does not interoperate with the reference

Dear Rudraksh2 Team, dear all,

Two findings, with a reproduction package that builds against the submitted trees (REF=) and modifies nothing under them.

1. Rudraksh2-512-I / -512-II fall short of the claimed 512-bit classical / 256-bit quantum level

Rudraksh2 instantiates G, H and the PRF/XOF with SM3 (spec Sec. 2.6.2), whose chaining value is 256 bits. On the 512 sets lenK = KEM_SYMBYTES = 64 bytes = exactly one SM3 block, so:

  - noiseseed is one block, hence s, e = CBD(pseudoXOF(noiseseed||i)) are a function of the 256-bit chaining value CV = CF(IV, noiseseed) alone (i, counter, padding, length are public constants);
  - in kem_enc, buf = m || H(pk) with m the first block, so the session key K = F(CF(IV,m), H(pk)).

We ran the unmodified kem_keygen / kem_enc and rebuilt, from a single 32-byte chaining value, (a) the secret key from CV(noiseseed) and (b) the session key from CV(m):

  Rudraksh2-512 secret key rebuilt from 256-bit SM3 chaining value: 50/50 exact
  Rudraksh2-512 session key  rebuilt from 256-bit SM3 chaining value: 50/50 exact

An attacker searches CV in {0,1}^256 (derive s, test b - A*s short; or recompute seed_r, re-encrypt, compare ct), i.e. about 2^256 classical / 2^128 Grover, versus the claimed 512 / 256. We do NOT run the search; the reduction to a 256-bit value is the point. The 256 sets meet their claim; the 128 sets stand classically (a 128-bit message caps quantum message-search at 2^64, i.e. the AES-128 situation, below the stated 80 but depth-model dependent). This is the same SM3-block mechanism noted for Weaver-2048; here it lands on the claimed level.

Fix: for the 512 sets use a XOF with chaining value / capacity >= 512 bits, or relabel 512-I/512-II.

2. The Cortex-M4 128/256 implementation uses a different error-correction constant

Additional_Implementations/Cortex_M4/lwekem{128,256}/.../minal.c:15 sets

    #define MINAL_BETA 0

The spec (Table 1: (B, beta) = (2, 220)), the reference, the AVX2 code, and Cortex-M4-512 all use 220. beta enters the 2-D B2-Minal code, so the M4 128/256 decapsulator recovers a different message:

  KAT vs submitted Test_Vectors:  m4-128 MISMATCH, m4-256 MISMATCH  (ref, AVX2, m4-512 MATCH)
  interop, 200 sessions each way:  enc=M4 dec=ref 0/200, enc=ref dec=M4 0/200  (ref<->AVX2 200/200)

Every honest M4<->reference session silently falls through to implicit rejection. By your own DFR table the beta=0 code is also worse (128-I 2^-94.5 vs <=2^-100; 256-I 2^-150.6 vs 2^-161). Fix: MINAL_BETA 220 (one line per file); the M4 128/256 KATs then match the Test_Vectors and interop is 200/200.

3. Minor

  - The -II sets use q=4001, but 2n does not divide q-1 (4000 = 2^5 * 5^3), so no primitive 2n-th root of unity exists at n=64/128/256 and the negacyclic NTT the spec defines (Eq. 1/2) is not computable for any -II set (max supported degree is 16). This is consistent with no -II implementation being shipped. The -II sets are also 4.5-6.4 bits below ML-KEM-512 in our lattice estimates (128-II CoreSVP 2^113.6; your Table 14 gives 2^114).
  - kem_dec and kem_enc ignore their length arguments (ct_len_bytes / pk_len_bytes) and always read the hard-coded size; a short buffer causes a heap-buffer-overflow READ in poly_decompress via unpack_ciphertext (ASAN). Same class as ngcc.dev kem-14-1, but a read, not a write.
  - Doc/code: Sec. 3.3.4 says "32-byte z" (code: 16/32/64 B); the spec writes G(H(pk)||m) but the code hashes m||H(pk); the compression premise log2 p < ceil(log2 q) is violated by 128-I and 512-I (u is not actually compressed).

We also checked and could not break: ciphertext malleability (no unused ciphertext bits; verify covers the full ciphertext; ~50k single-bit flips give 0 same-key), the 2-D B2-Minal decoder (ML-optimal in the honest-noise regime), and the constant-time property of the reference decode path (no secret-dependent branch/memory, 0 div). These are clean.
