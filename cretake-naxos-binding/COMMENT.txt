Dear CreTAKE Team, dear all,

Two implementation issues in the KEX wrappers (*/KEX_AlgorithmInstance.c), present
in both trees of the NICCS package.

Issue 1 (Critical). CreTAKE resists state leakage with the NAXOS trick
sk~ = wGen(G(ski, re)); the spec (4.2.1/4.2.2, Thms 3/4) claims revealing the state
alone leaks nothing. But G is instantiated as (S2S/S2K, e.g.
CreTAKE-S2S-BiT128-eZEN128/KEX_AlgorithmInstance.c:117,187):

    pseudohash(SEED_BYTES * 8, buf, SEED_BYTES + SKI_LEN, seed_kg);

The third argument is a BIT length (auxfunc.c:460) but the code passes the BYTE
count, so only r (64 B) plus the first 177/464/1072 bytes of ska are absorbed. In
BiT, pack_sk begins with the public key (pack_pk order; the code relies on this via
memcpy(pkI, ska, PKI_LEN)), and LCP(pk,sk) = 1048/2144/5056 >= those, so EVERY
absorbed byte is public: seed_kg = pseudohash(r || public-prefix-of-pk_i). The
ephemeral key no longer binds the long-term secret. A single permitted StateReveal
(state = r, resp. r||c_j||k_j) plus public data then recomputes seed_kg -> (tpk,tsk)
-> k~ -> the session key, with no search -- the model-level break class for which
kex-03-2 is Critical.

Ran (repro below; builds against the submission, does not modify it): 22 S2K/S2S
variants (Ref 12/12, Opt 10/12) recover 20/20, honest 20/20; a forged sk =
pk_i||random recovers 20/20; changing only this call to *8 drops recovery to 0/20.
K2K/K2S unaffected (there LCP = 0).

De-dup vs kex-03-1: it names this same call but judges it harmless on *entropy*
grounds. The right measure is the lost ephemeral/long-term binding. Vs kex-03-1
this adds a model-internal state-reveal recovery with no search, the S2K set, and
it survives the kex-03-1 responder-side fix (still 20/20). The authors' announced
uniform length fix would repair it; please verify with a StateReveal test, not KATs.

Issue 2 (Medium). kex_generate_pass2_msg_b / kex_derive_ss_a (void) the caller
message lengths and parse at constant offsets; no instance checks the length. For
K2S/K2K the first message is unsigned (pre-auth). Under ASan, sizing each buffer to
the bytes received, 149/150 truncated cases give heap-buffer-overflow READs (e.g.
READ 615 in poly_publickey_unpack <- pke_enc <- kex_generate_pass2_msg_b:148). Fix:
check length before splitting.

(Minor, Opt tree: ZEN instances vmovdqa the caller m1/m2 buffers, which the
interface need not align; six segfault on honest sessions at offset 16 mod 32 --
hence two ZEN256 Opt instances excluded above.)
