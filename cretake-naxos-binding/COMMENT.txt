Subject: Re: Round1: Public Comment: CreTAKE - the initiator-side units error removes the NAXOS state/long-term binding (a single state reveal recovers the session key), plus pre-authentication out-of-bounds reads

Dear CreTAKE Team, dear all,

We report two implementation issues in the KEX wrappers
(Implementations/{Reference,Optimized}_Implementation/*/KEX_AlgorithmInstance.c),
present in the archived NICCS package in both trees. Issue 1 concerns the same
initiator-side call as kex-03-1 (ngcc.dev); we do not claim a new code location,
but we think its impact has been measured wrongly and is in fact Critical. Issue 2
is, to our knowledge, not yet raised here or on ngcc.dev.

== Issue 1 (Critical). The units error removes the NAXOS binding; one state reveal recovers the key ==

1. Cause. CreTAKE resists state leakage with the NAXOS trick sk~ = wGen(G(ski, re)):
the ephemeral key is derived from BOTH the long-term secret ski and fresh
randomness re. The spec states (Sec. 4.2.1/4.2.2) that "revealing either the
signing key or the session state alone does not expose the wKEM secret", and the
proofs of Theorems 3/4 argue sk~ cannot be computed without both inputs. In
IND-StAA/IND-AA, revealing the session state alone (not the long-term key) is a
permitted query. The implementation instantiates G as (S2S shown; S2K identical;
kex_generate_pass1_msg_a and kex_derive_ss_a, e.g.
CreTAKE128/CreTAKE-S2S-BiT128-eZEN128/KEX_AlgorithmInstance.c:117,187):

    memcpy(buf + SEED_BYTES, ska, SKI_LEN);
    pseudohash(SEED_BYTES * 8, buf, SEED_BYTES + SKI_LEN, seed_kg);

The third pseudohash argument is a BIT length (auxfunc.c:460), but the code passes
the BYTE count SEED_BYTES + SKI_LEN. So only (SEED_BYTES + SKI_LEN)/8 bytes are
absorbed: r in full (64 B) plus the first 177/464/1072 bytes of ska at the
128/256/512 levels. Those leading ska bytes are PUBLIC: in BiT, pack_sk begins
with the packed public key in pack_pk order (the KEX code relies on this when it
recovers the peer key via memcpy(pkI, ska, PKI_LEN)). LCP(pk,sk) = 1048/2144/5056
(measured), and 177/464/1072 <= those, so EVERY absorbed ska byte is public. The
long-term secret bytes entering seed_kg number ZERO:

    seed_kg = pseudohash( r || (a public prefix of pk_i) ).

The ephemeral key now depends only on the state r and on public data; the NAXOS
binding to the long-term key is gone.

2. Attack (inside the model, no search). Given a single state reveal (state is r
for S2S; r || c_j || k_j for S2K) plus the public pk_i and the on-wire messages,
the attacker recomputes seed_kg, regenerates (tpk, tsk), decrypts to k~, and
recomputes the session key. This is a polynomial-time distinguisher under one
permitted StateReveal on the test session's owner with the peer uncorrupted -- the
same class of model-level break for which kex-03-2 is rated Critical.

3. What we ran (reproduction package below; builds against the submission via REF=,
copies the trees, does not modify them).
- 22 runnable S2K/S2S variants (Reference 12/12, Optimized 10/12 -- two ZEN256
  optimized instances segfault for the unrelated AVX2 alignment reason in the P.S.):
  session key recovered 20/20, honest sessions match 20/20.
- Public-data-only attacker: a "forged sk" = (pk_i || random garbage) after PKI_LEN
  still recovers 20/20.
- Causality control: changing only this call to (SEED_BYTES + SKI_LEN) * 8 drops
  recovery to 0/20, honest sessions still 20/20 (4 instances).
- LCP witness: absorbed_is_public = YES at all three levels.
- K2K/K2S are NOT affected (there the absorbed prefix is a KEM secret key with
  LCP(pk,sk) = 0, so 106-779 genuine secret bytes enter seed_kg).

4. Relation to kex-03-1 (de-duplication). kex-03-1 names this same call and judges
it harmless because "all 64 random bytes are still absorbed and this ... does not
reduce entropy further". That is right about entropy but measures the wrong thing:
the damage is the loss of the ephemeral/long-term binding on which NAXOS and
Theorems 3/4 rest. Relative to kex-03-1 this adds (a) a model-internal state-reveal
key recovery with no search; (b) a new affected set, S2K, for which kex-03-1 only
claimed a 2^64 weak-forward-secrecy loss after the complementary key is
compromised; and (c) it survives the responder-side fix named by kex-03-1 (we
re-ran with only that fix applied: still 20/20). We regard it as Critical whether
filed separately or folded into kex-03-1. The authors' announced uniform
length-parameter fix would also repair it; we suggest verifying the fix with an
explicit StateReveal test, since the KATs never exercise a state reveal.

== Issue 2 (Medium). Caller message lengths are ignored -> pre-authentication out-of-bounds reads ==

kex_generate_pass2_msg_b and kex_derive_ss_a discard the length arguments
((void)m1_len_bytes / (void)mb_len_bytes, or use them only to size a buffer) and
parse at constant offsets (m1 + TPK_LEN, m2 + C_TILDE_LEN, ...); no instance checks
the received length. For K2S/K2K the first message carries no signature, so this is
a PRE-authentication path. The clearest case is K2S,
tpk = calloc(m1_len_bytes,1); memcpy(tpk, m1, m1_len_bytes)
(CreTAKE-K2S-ZEN128-BiT128/KEX_AlgorithmInstance.c:127,135) -- buffer size is the
attacker's length field -- after which PKE_Encrypt reads TPK_LEN bytes from it.
Under ASan, allocating each buffer to exactly the bytes received (what a real
receiver does), 25 instances x {m1,m2} x L in {1,16,63} = 150 cases give 149
heap-buffer-overflow READs (one takes an early-exit branch); all reads, no OOB
write. Typical: READ of size 615 in poly_publickey_unpack (ZEN_128/poly.c:496) <-
pke_enc <- kex_generate_pass2_msg_b:148. Fix: validate the received length against
the expected length before splitting. We rate this Medium.

P.S. (minor, Optimized tree only). The ZEN-based optimized instances apply vmovdqa
directly to the caller-provided m1/m2 buffers, which the interface does not require
to be 32-byte aligned; six instances segfault on honest sessions when the message
length places the buffer at 16 mod 32 (test_correctness happens to get an aligned
buffer). This is why two optimized ZEN256 instances are excluded from Issue 1 above.
